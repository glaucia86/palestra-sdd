Spec-Driven Development: A evolução do TDD e BDD na era da IA generativa

01 / O que é SDD?

SDD — Spec-Driven Development

Uma abordagem de desenvolvimento onde especificações estruturadas (specs) são o artefato primário, guiando AI agents para gerar código de forma consistente e sem alucinações, com o humano no centro do processo.

  • Spec-First: a spec é escrita antes do código
  • Human-in-the-Loop: validação humana em cada etapa
  • Contexto estruturado: PRD, AGENTS, Rules e Skills
  • Rastreabilidade: cada decisão tem origem em uma spec

Analogia

Assim como um arquiteto precisa de plantas antes de construir, um AI agent precisa de specs antes de codificar.

SDD ≈ TDD, mas para especificações, não testes. A spec guia a implementação, não o contrário.

01 / SDD — Benefícios

Por que Adotar SDD?

Previsibilidade

O agente segue a spec, eliminando surpresas e desvios de requisitos durante a implementação.

Sem Alucinações

Contexto estruturado reduz drasticamente as alucinações do modelo de linguagem.

Documentação Viva

O PRD.md evolui junto com o projeto, sempre refletindo o estado atual do produto.

Rastreabilidade

Cada decisão técnica tem origem rastreável em uma spec aprovada pelo time.

Velocidade

Menos ciclos de revisão = implementações mais rápidas e com menor custo de mudança.

Comunicação

Specs alinham desenvolvedores, PMs e stakeholders em uma única fonte de verdade.

01 / Por que SDD hoje?

O Contexto de 2025/2026

Vivemos a era dos AI Coding Assistants. GitHub Copilot, Cursor, Gemini, Claude Code, Codex... Enfim, o desenvolvimento nunca foi tão rápido… e tão imprevisível.
  • Modelos geram código em segundos, mas sem contexto estruturado
  • Quanto maior o contexto, maior a chance de alucinação
  • Ciclos de revisão multiplicam o custo de desenvolvimento
  • Retrabalho consome até 30–40% do tempo dos times

Problema Central

Os AI agents são poderosos, mas precisam de contexto estruturado para produzir resultados consistentes.

SDD é a Resposta

Specs funcionam como um "contrato" entre o desenvolvedor e a IA.

01 / Por que SDD hoje? — Princípios

SDD como Resposta para a IA

Spec-First

A especificação é o artefato de maior valor. Código, testes e docs são derivados da spec, não o contrário.

Human-in-the-Loop

O humano revisa e aprova cada spec antes que o agente implemente. A IA executa, o humano decide.

Architecture-First

"Spec-first" é o análogo de "Architecture-first" para sistemas de IA. A estrutura guia a construção.

Rastreabilidade

Cada linha de código pode ser rastreada até um requisito aprovado. Auditoria e rollback ficam triviais.

💬 "Não deixe a IA improvisar. Dê a ela uma spec bem escrita e ela entregará exatamente o que você precisa."

02 / spec-kit

spec-kit — O Toolkit do SDD

O spec-kit é um toolkit open source mantido pelo GitHub que permite focar em cenários de produto e resultados previsíveis, em vez de "vibe coding" cada pedaço do zero. Ele operacionaliza o SDD com um CLI e slash commands para agentes IA.

  • Open Source — MIT License · github/spec-kit
  • +70k estrelas no GitHub · 79 contribuidores
  • Mantido pelo GitHub, inspirado na pesquisa de John Lam
  • Specify CLI — installável via uv tool install
  • Slash Commands nativos nos agentes IA (/speckit.*)

Missão

"Build high-quality software faster. Focus on product scenarios and predictable outcomes — not vibe coding."

💡 spec-kit ≠ vibe coding. Cada linha de código é rastreada até um requisito aprovado pelo humano.
🤖 Compatível com: GitHub Copilot, Claude Code, Cursor, Gemini CLI, Windsurf, Codex CLI e +20 agentes!

02 / spec-kit — Instalação

Instalando o spec-kit

Opção 1 — Instalação Permanente (recomendada)

# Instala uma vez, usa em qualquer projeto
uv tool install specify-cli \
  --from git+https://github.com/github/spec-kit.git

# Verifica ferramentas disponíveis
specify check

Opção 2 — Uso Único (sem instalar)

uvx --from git+https://github.com/github/spec-kit.git \
  specify init <PROJECT_NAME>
📋 Pré-requisitos: Python 3.11+, uv, Git e um agente IA suportado.

Inicializar Projeto

# Novo projeto com GitHub Copilot
specify init meu-projeto --ai copilot

# Em projeto existente
specify init --here --ai copilot

# Windows (PowerShell)
specify init meu-projeto --ai copilot --script ps

# Com AI Skills integradas
specify init meu-projeto --ai copilot --ai-skills

# Com Claude Code
specify init meu-projeto --ai claude
🔧 O specify init configura: templates, slash commands (/speckit.*) e estrutura de pastas automaticamente.

02 / spec-kit — PRD.md

PRD.md — Ponto de Partida

Você idealiza o projeto e cria via prompt o PRD.md. Em seguida, usa um prompt junto com /speckit.specify para que o agente leia esse arquivo e inicie o ciclo: specify → plan → tasks → implement.

# PRD: [Nome do Projeto]

## 1. Visão Geral
Descrição concisa do produto e objetivos.

## 2. Requisitos Funcionais
- **RF01**: O sistema deve...
- **RF02**: O sistema deve...

## 3. Requisitos Não-Funcionais
Performance, segurança, acessibilidade.

## 4. Critérios de Aceite
- **CA01**: Testável e verificável...

## 5. Perguntas Abertas
- Ambiguidades a resolver...
Por que PRD.md importa para a IA?
  • Use IDs únicos RF01, CA01 para rastreabilidade
  • Critérios de aceite testáveis e objetivos
  • Versionado no Git — histórico de decisões
  • Lido por humanos e máquinas
Sem PRD.mdCom PRD.md
Contexto vago e efêmeroContexto estruturado e persistente
Alucinações frequentesAlucinações drasticamente reduzidas
Rastreabilidade impossívelAutomática via IDs (RF, CA)
Onboarding lentoRápido via PRD.md + AGENTS.md

03 / GitHub Copilot Chat — Modos

Os 4 Modos do Copilot Chat

Ask Mode

Modo conversacional — faça perguntas, obtenha explicações, debata arquitetura. O Copilot responde mas não altera arquivos. Ideal para exploração.

Explore Mode

Exploração read-only — navega o codebase com ferramentas de leitura (Grep, Glob, Read). Ideal para entender uma base desconhecida sem fazer modificações. Disponível por enquanto na versão Visual Studio Code Insiders.

Agent Mode ✦

Modo autônomo — executa tarefas de ponta a ponta: analisa o codebase, decide quais arquivos mudar, roda comandos no terminal e itera até concluir. O modo ideal para SDD.

Plan Mode

(Public preview) — O Copilot cria um plano de implementação detalhado para revisão humana antes de qualquer mudança de código. Perfeito para SDD!

Explore → Plan → Agent: explore o codebase, crie o plano, execute com contexto estruturado. O fluxo completo do SDD.

04 / Arquitetura — AGENTS.md

AGENTS.md — O Contrato Vivo

AGENTS.md é um padrão aberto para comunicar aos AI agents o contexto, regras e comportamentos esperados de um repositório. Posicionado na raiz do projeto, é lido automaticamente pelos agentes modernos.

Localização

Sempre na raiz do repositório — ./AGENTS.md

Documento Vivo

Atualizado junto com o projeto, reflete sempre o estado atual.

# AGENTS.md

## Objetivo do Projeto
API REST de gerenciamento de tarefas.

## Stack Tecnológico
- Node.js 22 + TypeScript strict
- Express 5 + Prisma ORM
- PostgreSQL 16
- Vitest para testes

## Convenções de Código
- Nomenclatura: camelCase para variáveis
- Imports: sempre absolutos (src/...)
- Erros: nunca use `any`, use Result types

## DO ✅
- Escreva testes para cada função pública
- Use TypeScript strict mode
- Documente endpoints com JSDoc

## DON'T ❌
- Não use `any` type
- Não faça commit sem testes passando
- Não altere o schema sem migração
04 / Arquitetura — Rules

Rules — Diretrizes Globais

Rules são diretrizes globais que definem o comportamento padrão do agente para todo o workspace, independente do projeto ou tarefa específica.

📌 No GitHub Copilot, as Rules são configuradas em arquivos .github/copilot-instructions.md ou .instructions.md.
As Rules são o "modo padrão" do agente. AGENTS.md pode sobrescrever Rules para um projeto específico.

DO — Sempre fazer

  • Use TypeScript strict mode
  • Escreva testes para funções públicas
  • Documente APIs com OpenAPI/JSDoc
  • Siga os padrões SOLID e Clean Code
  • Valide inputs em toda boundary externa

DON'T — Nunca fazer

  • Usar any type no TypeScript
  • Commitar sem testes passando
  • Hardcodar credenciais ou segredos
  • Ignorar erros silenciosamente (empty catch)

05 / Progressive Disclosure

Progressive Disclosure

Progressive Disclosure é o princípio de revelar apenas o contexto necessário para a tarefa atual. Em SDD, isso significa dividir o conhecimento do agente em camadas — carregando informação especializada sob demanda, economizando tokens e reduzindo ruído.

  • AGENTS.md raiz: mínimo, global, estável — regras que valem para todas as tarefas
  • Skills especializadas: carregadas sob demanda, apenas quando necessário
  • Context Window: até 70% de economia de tokens
  • Qualidade: menos ruído = respostas mais precisas e consistentes

Analogia

Como um médico especialista — o clinico geral cuida do básico; o especialista é chamado apenas quando o problema exige. O contexto funciona igual: carregue o especialista só quando precisar.

📊 AGENTS.md minimalista + Skills sob demanda pode reduzir em até 70% o uso de context window por sessão.

- Não faça commit sem testes passando

05 / Progressive Disclosure — Princípios

6 Princípios do Progressive Disclosure

1. Minimalismo

AGENTS.md deve conter apenas regras necessárias para todas as tarefas do repositório. Regras específicas ficam em arquivos secundários.

2. Separação

Instrução especializada → arquivo secundário (docs/agents/). Nada de "documento gigante" com tudo dentro.

3. Delegação

AGENTS.md raiz declara onde encontrar instruções especializadas via links. O agente busca quando precisar.

4. Acionabilidade

Prefira instruções diretas: "Antes de alterar código, explique o motivo." Evite textos genéricos como "siga boas práticas".

5. Estabilidade

Estruturas de pastas e informações instáveis não devem ir ao AGENTS.md raiz — apenas a arquivos secundários.

6. Economia

Cada token economizado = respostas mais rápidas e baratas. AGENTS.md enxuto eleva qualidade e reduz custo por sessão.

📚 Esses arquivos especializados também são chamados de "Skills" na comunidade de AI Agents (Claude Code, Cursor, etc.) — mesmo conceito, carregamento sob demanda.
