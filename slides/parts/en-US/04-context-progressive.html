04 / Architecture - AGENTS.md

AGENTS.md — The Living Contract

AGENTS.md is an open standard to communicate repository context, rules, and expected behavior to AI agents. Placed at the project root, it is read by multiple tools and agents (depending on product/integration), acting as a "README for agents".

Location

Always at the repository root — ./AGENTS.md

Living Document

Updated alongside the project, always reflecting the current state.

# AGENTS.md

## Project Goal
Task management REST API.

## Tech Stack
- Node.js 22 + TypeScript strict
- Express 5 + Prisma ORM
- PostgreSQL 16
- Vitest for tests

## Code Conventions
- Naming: camelCase for variables
- Imports: always absolute (src/...)
- Errors: never use `any`; use Result types

## DO ✅
- Write tests for each public function
- Use TypeScript strict mode
- Document endpoints with JSDoc

## DON'T ❌
- Do not use `any` type
- Do not commit without passing tests
- Do not change schema without migration

AGENTS.md is the "README for agents" — it's the first thing an AI agent reads to understand the project. Location at the root is intentional: it's always discoverable, regardless of which file or directory the agent is working in.

"Living document" is the key phrase: AGENTS.md should be updated alongside the code, not written once and forgotten. When the tech stack changes, when conventions evolve, AGENTS.md changes too.

The example in the slide is a real minimal template. Note the explicit DO/DON'T structure: these are the clearest format for agent instructions. Avoid abstract guidelines like "follow best practices" — be specific and testable.

Closing: AGENTS.md is the persistent context that survives across sessions, team members, and model changes. Invest in it like you invest in tests.

04 / Architecture - Rules

Rules — Global Guidelines

Rules are global guidelines that define the default agent behavior across the whole workspace, regardless of project or task.

📌 In GitHub Copilot, Rules use .github/copilot-instructions.md as primary and also .github/instructions/** (when supported).
Rules are the agent "default mode". AGENTS.md can override Rules for a specific project.

DO — Always do

  • Use TypeScript strict mode
  • Write tests for public functions
  • Document APIs with OpenAPI/JSDoc
  • Follow SOLID and Clean Code principles
  • Validate inputs at every external boundary

DON'T — Never do

  • Use any type in TypeScript
  • Commit without passing tests
  • Hardcode credentials or secrets
  • Silently ignore errors (empty catch)

Rules are the workspace-level guardrails that apply regardless of project or task. In Copilot, copilot-instructions.md is the primary vehicle. The distinction from AGENTS.md is scope: AGENTS.md is project-specific, Rules are workspace/organization-wide.

The DO/DON'T format is intentional: it maps directly to how agents parse instructions. Positive rules (always do X) and negative rules (never do Y) are processed differently — both are needed.

The security-focused DON'Ts (no hardcoded credentials, no silent errors) are non-negotiable. These are OWASP-aligned guardrails that the agent should enforce by default in every session.

Closing: Rules are the safety net. AGENTS.md provides project context. Together they ensure the agent operates within defined boundaries at all times.

04 / Architecture - Skills.md

Skills.md — Specialized Knowledge

Skills are directories with a SKILL.md file as entry point — an open agentskills.io pattern adopted by GitHub Copilot in Dec/2025. The agent keeps the description in context and loads full skill content only when needed: Progressive Disclosure in practice.

Performance

Fewer tokens used = more efficient and cheaper sessions.

Portability

Skills work in VS Code, Claude, and other AI tools.

📖 See section 05 for a deep dive into Progressive Disclosure — principles, layered structure, and best practices.
Real examples (clickable):
find-skills · vercel-react-best-practices · web-design-guidelines · frontend-design
🎯 Load only the Skill for the current task to reduce noise and token usage in context.

Skills are the most powerful and underused layer of the context architecture. They solve a fundamental token economy problem: you can't load all domain knowledge into every prompt, so you load only what's relevant to the current task.

The agentskills.io pattern is open and portable: the same skills work across Copilot, Claude, Cursor, and other tools. This avoids tool lock-in on your domain knowledge investment.

Practical workflow: when starting a React task, instruct the agent to load `skills/react-patterns.skill.md`. When working on API design, load `skills/api-design.skill.md`. Each skill is focused, maintained, and reusable.

Closing: skills are the mechanism that makes Progressive Disclosure concrete — which is exactly what section 05 covers next.

Reveal only the necessary context, at the right time — the secret to an efficient agent

Progressive Disclosure is the advanced context strategy that turns context architecture into a token-efficient, high-quality operational system. This section goes deeper than "load an AGENTS.md" — it explains how to structure context across multiple layers.

The doctor analogy in the slide is helpful: a general practitioner handles basics; a specialist is called only when needed. Context works the same way — load specialized knowledge only when the current task requires it.

05 / Progressive Disclosure

Progressive Disclosure

Progressive Disclosure is the principle of revealing only the context needed for the current task. In SDD, this means layering the agent's knowledge — loading specialized information on demand, saving tokens, and reducing noise.

  • Root AGENTS.md: minimal, global, stable — rules that apply to all tasks
  • Specialized Skills: loaded on demand, only when needed
  • Context Window: up to 70% token savings (ref. LinkedIn — Glaucia Lemos)
  • Quality: less noise = more precise and consistent responses

Analogy

Like in medicine: a general practitioner handles basics; a specialist is called only when needed. Context works the same way.

📊 A minimal AGENTS.md + on-demand Skills approach can reduce context-window usage by up to 70% per session. (ref. LinkedIn — Glaucia Lemos)

Progressive Disclosure in practice: the root AGENTS.md stays minimal and stable — only rules that apply to all tasks all the time. Everything specialized lives in secondary files, loaded on demand.

The "up to 70% token savings" figure comes from my own structured workflow measurements — documented in my LinkedIn article. Your mileage will vary, but the direction is consistent: leaner context = faster responses, lower cost, less noise.

The quality point is crucial: it's not just about tokens. Less context noise means the agent focuses on what matters for the current task, producing more precise and consistent outputs.

Arrows 1–4: Root AGENTS.md (global) → Specialized Skills (on-demand) → Context Window efficiency → Quality improvement. Closing: Progressive Disclosure is the operational implementation of "right context, right time, right task."

AGENTS.md — Minimal Example

# AGENTS.md

## Project
Task management API with JWT.

## Global Rules
- TypeScript strict mode
- Mandatory tests for public functions
- Never use `any` type

## Specialized Instructions
- Testing: docs/agents/testing.md
- Architecture: docs/agents/architecture.md
- Security: docs/agents/security.md

## Agent Limits
- Do not change schema without migration
- Do not commit without passing tests
💡 AI generates specialized files automatically - you do not need to create them manually!

The layered folder structure is the practical implementation of Progressive Disclosure. The root AGENTS.md points to specialized files but doesn't load them — they're fetched only when explicitly requested for a task.

The "AI generates specialized files" point is important for adoption: you don't need to write every docs/agents/*.md file from scratch. Use spec-kit or Copilot to generate the initial versions from your AGENTS.md. Then refine iteratively.

The AGENTS.md minimal example in the slide shows the delegation pattern: each section points to where the agent can find more detail, without loading all that detail upfront.

Closing: the layered structure is a one-time investment that pays compound interest — every future session benefits from cleaner, faster context loading.

05 / Progressive Disclosure — Principles

6 Principles of Progressive Disclosure

1. Minimalism

AGENTS.md should contain only rules required for all repository tasks. Specific rules belong in secondary files.

2. Separation

Specialized instruction → secondary file (docs/agents/). Avoid one giant document with everything inside.

3. Delegation

Root AGENTS.md declares where to find specialized instructions through links. The agent fetches them when needed.

4. Actionability

Prefer direct instructions: "Before changing code, explain why." Avoid generic text like "follow best practices".

5. Stability

Unstable folder structures and volatile information should not go in root AGENTS.md - keep them in secondary files.

6. Efficiency

Every saved token = faster and cheaper responses. A lean AGENTS.md improves quality and lowers per-session cost.

📚 These specialized files are also called "Skills" in the AI agent community (Claude Code, Cursor, etc.) — same concept, on-demand loading.

The six principles are the actionable checklist for implementing Progressive Disclosure: Minimalism, Separation, Delegation, Actionability, Stability, Efficiency. Each principle directly addresses a failure mode of naive context management.

"Actionability" deserves special attention: specific instructions like "before changing code, explain why" are infinitely more useful than "follow best practices." The agent can act on specific instructions; it interprets abstract ones unpredictably.

The community convergence point — Claude Code, Cursor, and others all using similar "Skills" patterns — validates that this approach is emerging as an industry standard, not a one-off technique.

Closing: these six principles are the implementation guide for the context architecture. Follow them and the architecture becomes self-maintaining as the project evolves.
