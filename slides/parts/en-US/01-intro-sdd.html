Section 01

SDD

Spec-Driven Development: the evolution of TDD and BDD in the generative AI era

Let's start with the foundation: what SDD is and why it became so relevant now that we have agents with multi-step execution.

The central question is no longer "can AI do this?" — that's already clear. The question now is: "how do I make AI do this in a predictable and repeatable way?" SDD answers that second question.

01 / What is SDD?

SDD - Spec-Driven Development

A development approach where structured specifications (specs) are the primary artifact, guiding AI agents to generate code consistently with fewer hallucinations, while humans remain at the center.

  • Spec-First: the spec is written before code
  • Human-in-the-Loop: human validation at every step
  • Structured context: PRD, AGENTS, Rules, and Skills
  • Traceability: every decision originates from an approved spec

Analogy

Just like an architect needs blueprints before building, an AI agent needs specs before coding.

Teaching analogy: SDD ~= TDD, but for specifications, not tests.

SDD does not replace TDD/BDD: SDD defines the "what" and "why"; tests validate behavior.

↓ press ↓ to continue in this section

When I talk about SDD, I'm talking about treating specification as an executable engineering artifact — not as decorative documentation that ages in a folder.

The blueprint analogy is still the most direct: without a blueprint, construction happens by improvisation. With AI it's the same — the human defines intent, limits, and acceptance criteria; the agent executes within that contract. Without that contract, each session starts almost from scratch.

To reinforce: SDD complements tests, code review, and security — it doesn't replace them. That becomes clear in the next slide.

Arrow 1 — Spec-First: the spec exists before the code. Arrow 2 — Human-in-the-Loop: human validation at each critical step. Arrow 3 — Structured Context: the four layers we'll see in detail. Arrow 4 — Traceability: every decision traceable back to an approved spec. Closing: predictability is a direct consequence of specification quality.

01 / SDD - Limits and Risks

SDD reduces ambiguity, but it does not replace:

  • Automated testing
  • Code review
  • Threat modeling / security review
  • Evals (even qualitative)
🎯 SDD increases predictability. Final quality still depends on continuous technical validation.

This slide exists to keep us grounded: SDD doesn't replace engineering discipline. Automated tests, code review, security, and evals remain mandatory.

Without these practices, SDD only accelerates mistakes more efficiently. The metaphor I use: you can build faster with better blueprints, but you still need a building inspector.

Arrows 1 to 4: Tests → Code Review → Threat modeling/security → Evals. Closing: without continuous validation, AI only accelerates errors — with validation, AI amplifies quality.

01 / Why SDD today?

The 2025/2026 Context

We are in the era of AI coding assistants. Development has never been faster - or more unpredictable.
  • Models generate code in seconds, often without structured context
  • Larger context increases hallucination risk
  • Review loops multiply engineering cost
  • Rework can consume 30-40% of team time (ref. software engineering productivity surveys)

Core Problem

AI agents are powerful, but they need structured context for consistent outcomes.

SDD is the Answer

Specs act as a contract between developer and AI.

The current scenario is this: agents like GitHub Copilot, Cursor, and Claude Code are much more capable — multi-step execution, terminal access, files, and external tools. But this expanded capability doesn't resolve poorly defined context. In fact, more autonomy with poor context amplifies the cost of errors.

On the "30-40% rework" data point in the slide: this is an estimate that circulates in software engineering productivity surveys, but without a single universal primary source. Use it as an order-of-magnitude reference — the correct point is that rework from poorly defined context is expensive and measurable. Measure it in your own team.

Arrow 1 — fast code without structured context. Arrow 2 — more capability with poor context amplifies hallucination. Arrow 3 — review cycles have growing cost. Arrow 4 — rework as an economic fact for the team. Closing: SDD enters specifically to resolve this context gap — it's not extra complexity, it's variability reduction.
