06 / Harness Engineering — What is it?

Agent = Model + Harness

The model is the brain.
The harness is everything around it.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering designs instructions, tools, environment, state, feedback, and observability to make agent work reliable.

  • A subset of Context Engineering: focused on the agent operating system, not just the prompt
  • The problem it solves: two agents with the same model and same task produce radically different results — the difference is in the harness
  • Emergent vocabulary: HumanLayer, Martin Fowler, OpenAI, and Walking Labs offer complementary perspectives

Formula 1

The model is the driver — talented, but limited without support. The harness is the track + pit crew + telemetry: what enables a fast lap, safely.

Replacing the driver with a faster one rarely solves the problem — the bottleneck is usually the harness.

Harness Engineering = tending to the pit crew with the same rigor you apply to the driver

Technical: Agent = Model + Harness separates model capability from the system that provides instructions, tools, environment, state, feedback, and observability.

Executive impact: before paying for more capability, the team can locate the layer that constrains reliable execution.

Control and KPI: track first-pass acceptance, regressions, retries, and review time per harness configuration.

Caveat: the Formula 1 analogy is instructional; failures can be in the model or the harness and require evidence for attribution.

06 / Harness Engineering — Framework

Guides & Sensors

Martin Fowler's framework — feedforward (before) + feedback (after)

Guides (feedforward)

Steer the agent BEFORE it acts — increase the probability of getting it right the first time

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, few-shot examples, semantic context

Sensors (feedback)

Observe AFTER the agent acts — detect issues and enable course correction

Computational
Tests, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, code review agent, semantic analysis

GPS = Guide feedforward
tells you where to turn before the curve

Speed camera = Sensor feedback
detects the error after it happened

Guides prevent; Sensors prove and correct.

Objective rule: deterministic checker first.
Inferential judgment: selective; never the only oracle.

Technical: Guides act before; Sensors observe after. Both can be computational or inferential.

Executive impact: prevention reduces rework, while feedback produces evidence to correct and govern execution.

Control and KPI: for an objective rule, run tests, lint, or typecheck before semantic judgment; measure coverage and false positives.

Caveat: an inferential sensor is probabilistic and selective; it does not replace a deterministic oracle when the rule is executable.

06 / Harness Engineering: Operationalization

The Harness that Scales

It is not “a better prompt”. It is a lean operating system for agents to work with evidence.

Repo as source

Critical knowledge must live in the repository: architecture, commands, constraints, and decisions.

Agent Skills

AGENTS.md routes; SKILL.md loads specialized knowledge on demand.

Maker / Checker

High-risk change separates who produces from who verifies criteria and evidence.

WIP = 1

One active unit at a time, with acceptance criteria and executable completion evidence.

State + Observability

State, logs, traces, checks, and history make progress and failure auditable.

Limits ≠ Proof

Sandbox and approvals limit action; tests and review prove the result.

Recurring failure: attribute it to instruction, tool, environment, state, feedback, or observability before changing the model.

Technical: maker/checker, limited WIP, state, and observability reduce correlated error, dispersion, and continuity loss.

Executive impact: each unit ends with reviewable evidence, a clear owner, and a controlled blast radius.

Control and KPI: track WIP, checks per slice, restarts without rediscovery, regressions, and failures by harness layer.

Caveat: sandbox and approvals reduce the capacity for harm, but do not prove correctness; tests and review remain necessary.

06 / Harness Engineering — Temporal bridge

Handoff preserves. Harness executes. Loop reconciles.

Each layer answers a different question and hands state to the next.

SDD

Intent

contract + criteria

Slice

Unit

scope + evidence

Handoff

Continuity

state + owner

Harness

Execution

guides + checks

Loop

Time

repeat · stop · escalate

Temporal dimension: who triggers, how work progresses, what survives across runs, and when it must stop.
Now we move from designing only the environment to designing the system that activates it.

Technical: SDD defines the contract, the Slice bounds work, the Handoff preserves state, the Harness provides execution and signals; Loop Engineering adds trigger, progression, and stop.

Executive impact: the chain separates intent, accountability, evidence, and automation without hiding the human gate.

Control and KPI: each transition must produce an owner, terminal state, and evidence; measure accepted outcomes, retries, and restart time.

Caveat: this is a narrative bridge. The next section presents Loop Engineering as an emergent term, not a consolidated formal standard.
