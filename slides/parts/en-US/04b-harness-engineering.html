Closing the loop between spec and production gate

This is the most emerging topic of the talk — gaining traction in 2026 as teams scale autonomous agents and face a critical question: how do you ensure that automatically generated code is safe, correct, and aligned with the spec?

The term "Harness Engineering" was coined by Viv (HumanLayer, 2025) and gained momentum through Martin Fowler's article and OpenAI's Codex scale experiment. The core idea: if the agent is the sum of the model plus everything around it, then "Harness Engineering" is the practice of tending to that "everything around it" with the same rigor you apply to production code.

Present this as a natural extension of SDD — not a new framework to learn from scratch.

06 / Harness Engineering — What is it?

Agent = Model + Harness

The model is the brain.
The harness is everything around it.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering is the practice of designing instructions, tools, environment, state, and feedback to make agent work reliable.

  • A subset of Context Engineering: focused on the agent operating system, not just the prompt
  • The problem it solves: two agents with the same model and same task produce radically different results — the difference is in the harness
  • Coined by Viv (HumanLayer) · documented by Martin Fowler · popularized by OpenAI's Codex scale experiment
🏎️

Formula 1

The model is the driver — talented, but limited without support. The harness is the track + pit crew + telemetry: what enables a fast lap, safely.

Replacing the driver with a faster one rarely solves the problem — the bottleneck is usually the harness.

Harness Engineering = tending to the pit crew with the same rigor you apply to the driver

The "Agent = Model + Harness" equation comes from the HumanLayer blog (Viv, 2025) and is the most compact way to explain why switching the model is rarely the right answer to agent quality issues. In most cases, the problem is the harness — the quality of instructions, the context provided, the feedback mechanisms.

The Walking Labs learning material reinforces the operational view: a harness is not a prompt file. It is the set of instructions, tools, environment, persistent state, and feedback that determines how much model capability becomes reliable execution.

Context Engineering is the broader term — Harness Engineering is a subset focused on the system around the agent: what it receives before acting (guides), what it may execute, how it preserves state, and what checks it after acting (sensors).

Arrow 1 — subset of Context Engineering. Arrow 2 — the problem it solves. Arrow 3 — origin of the term (Viv, Fowler, OpenAI). Closing: focus on the harness, not just the model.

06 / Harness Engineering — Framework

Guides & Sensors

Martin Fowler's framework — feedforward (before) + feedback (after)

Guides (feedforward)

Steer the agent BEFORE it acts — increase the probability of getting it right the first time

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, few-shot examples, semantic context

Sensors (feedback)

Observe AFTER the agent acts — detect issues and enable course correction

Computational
Tests, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, code review agent, semantic analysis

GPS = Guide feedforward
tells you where to turn before the curve

Speed camera = Sensor feedback
detects the error after it happened

Good harnesses combine both, but prefer Guides.

Computational = deterministic, fast, runs always.
Inferential = semantic, expensive, runs selectively.

Martin Fowler's framework (harness-engineering.html article, 2025) divides harness mechanisms on two axes: how they act (feedforward = Guides; feedback = Sensors) and how they are implemented (Computational = deterministic; Inferential = AI-based).

The key intuition: Guides are cheaper than Sensors because they prevent the error before it happens. A well-written AGENTS.md (Computational Guide) is infinitely cheaper than a code review agent (Inferential Sensor) running on every commit. Invest in Guides first.

06 / Harness Engineering: Operationalization

The Harness that Scales

It is not “a better prompt”. It is a lean operating system for agents to work with evidence.

Repo as source

Critical knowledge must live in the repository: architecture, commands, constraints, and decisions.

Routing files

AGENTS.md points the way. Details live in docs/skills on demand.

Initialization

Before coding: environment runs, tests execute, and the task is split into verifiable steps.

WIP = 1

One active unit at a time, with acceptance criteria and executable completion evidence.

Observability

Logs, traces, checks, rubrics, and history make “looks right” auditable.

Clean exit

A session only ends with build/tests, progress, artifacts, and next step in a clear state.

Practical rule: when the agent fails, inspect the harness first: vague task, invisible context, broken environment, missing feedback, or lost state.

This slide synthesizes the Walking Labs learning material. The key idea: Harness Engineering is not just prompt writing or AGENTS.md. It is the agent's operating system.

Repo as source: for an agent, what is not in the repository practically does not exist. Routing files: AGENTS.md should be short and point to specialized documentation according to the task — this connects directly to Progressive Disclosure.

Initialization separates setup from implementation. WIP=1 reduces overreach: the agent stops opening five fronts and finishes one verifiable unit.

Observability turns subjective review into evidence: logs, traces, tests, rubrics, and acceptance criteria. Clean exit closes the loop: build/tests/progress/artifacts must be in order so the next session does not start from zero.

06 / Harness Engineering — Connection with SDD

SDD + Harness = Closed Loop

Your SDD artifacts already are harness components — what's missing is recognizing and operationalizing them as such.

SDD Artifact Role in Harness
spec.md / PRD.md Computational Guide — feedforward with structured intent
AGENTS.md Computational Guide — rules and constraints for the agent
Acceptance Criteria (AC) Defines Sensor targets — "passed = spec-compliant"
Tests (CI/CD) Computational Sensor — deterministic feedback
Skills.md Inferential Guide — specialized context on demand
If you practice SDD, you are already doing Harness Engineering.
Harness Engineering is the name for what you do when you tend to SDD artifacts with operational rigor.

The cycle

① Spec (SDD) → feedforward Guide for the agent
② Agent generates → Computational Sensor evaluates
③ Failed → iterate until Sensors pass
④ Passed → human reviews result, not process
Codex, by OpenAI (2025): "Our biggest challenges now center on designing environments, feedback loops, and control systems" — 1 million lines of code with zero manually written lines.

The table bridges what the audience already knows (SDD artifacts) with the new vocabulary (Guides/Sensors). There's nothing new to learn — it's about recognizing what they already do with the right name and an explicit framework.

The Codex quote is powerful: in 2025, the Codex team reported 1 million lines of code with zero manual intervention — and they described their biggest challenge not as the model, but as "designing environments, feedback loops, and control systems". That is the operational definition of Harness Engineering.
