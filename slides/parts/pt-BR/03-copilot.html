03 / AI Coding Agents

De Assistente para Agente

Um AI Coding Agent entende requisitos, navega pelo repositório, altera arquivos, executa comandos, revisa diffs e aprende com feedback. A diferença não está só no modelo: está no harness ao redor dele.

  • IDE agents
    Copilot Chat, Cursor, extensões e contexto de editor.
  • CLI agents
    Codex CLI, Copilot CLI, Gemini CLI e automações locais.
  • App/Cloud agents
    Codex App, worktrees, cloud environments e tarefas paralelas.

Spec

Define intenção, escopo e critérios.

AGENTS

Define regras e comportamento do repo.

Skills

Carregam especialização sob demanda.

Checks

Validam se a entrega bate com a spec.

Tese: modelo muda, produto muda, preço muda. O contrato SDD permanece.

Use este slide para separar ferramenta de método. GitHub Copilot, Codex, Cursor e Claude Code têm interfaces diferentes, mas todos sofrem com o mesmo problema: se o contexto é ruim, a entrega fica instável.

A resposta do SDD é construir uma superfície de contexto reutilizável: spec, AGENTS, Skills e checks. Isso reduz dependência de produto e aumenta previsibilidade.

03 / GitHub Copilot Chat

GitHub Copilot Chat

Powered by AI
GPT-5.3-Codex Claude Sonnet 4.6 Claude Opus 4.6 Gemini 3.1 Pro +20 modelos

O GitHub Copilot Chat é a interface conversacional do Copilot. Permite fazer perguntas em linguagem natural sobre código, gerar implementações, depurar e, no Agent Mode, executar tarefas complexas de forma totalmente autônoma.

  • Completions em tempo real enquanto você digita
  • Chat Panel para Q&A, explicações e refatoração
  • Inline Chat ( Ctrl+I ) diretamente no editor
  • Agent Mode — execução autônoma e multi-etapas
  • Multi-modal — aceita screenshots como contexto

Copilot Chat precisa ser entendido como interface de colaboração técnica — não apenas autocomplete. A diferença prática está em três níveis de uso: conversar para entender (Ask Mode), editar inline para iterar rapidamente (Edit Mode e Inline Chat), e executar fluxos complexos com autonomia crescente (Agent Mode + Plan Mode).

Nota sobre modelos: a lista mostrada no slide de modelos é uma fotografia de 27/02/2026. Modelos são adicionados, ajustados e retirados com frequência — para trabalho de produção, sempre valide em docs.github.com/en/copilot/reference/ai-models/supported-models antes de definir estratégia.

Setas 1 a 5: Completions → Chat Panel → Inline Chat (Ctrl+I) → Agent Mode → Multimodal com imagens. Fechamento: capacidade sem contexto estruturado ainda gera variabilidade — é aí que SDD entra.

03 / GitHub Copilot Chat — Modos

Os 4 Modos do Copilot Chat

Ask Mode

Modo conversacional — faça perguntas, obtenha explicações, debata arquitetura. O Copilot responde mas não altera arquivos. Ideal para exploração.

Edit Mode

Edições diretas e focadas no editor — inline, multi-file, ou via Ctrl+I. Ideal para iterações rápidas sem sair do contexto de código.

Agent Mode ✦

Modo autônomo — executa tarefas de ponta a ponta: analisa o codebase, decide quais arquivos mudar, roda comandos no terminal e itera até concluir. O modo ideal para SDD.

Plan Mode

O Copilot cria um plano de implementação detalhado para revisão humana antes de qualquer mudança de código. Perfeito para SDD.

Ask → Plan → Agent: entenda o codebase, crie o plano, execute com contexto estruturado. O fluxo completo do SDD.

Atenção crítica para audiência técnica: os modos oficiais do Copilot Chat na IDE, conforme documentado em docs.github.com, são quatro — Ask, Edit, Agent e Plan. O slide apresenta "Explore Mode" no lugar de "Edit Mode", o que merece esclarecimento direto.

"Explore" funciona bem como estratégia de trabalho — usar o agente para navegar e entender o codebase com ferramentas de leitura antes de qualquer edição. Mas não é um modo oficial no dropdown da IDE. O modo para edições diretas e focadas é o Edit Mode. Para exploração read-only estruturada, você pode usar Ask Mode ou Agent Mode com ferramentas de leitura.

Nomenclatura oficial para reforçar: Ask (conversacional, sem alterar arquivos) → Edit (edições diretas no editor) → Plan (plano detalhado para revisão humana antes de qualquer mudança) → Agent (execução autônoma ponta a ponta, modo central para SDD).

O fluxo recomendado para SDD: Ask (entenda) → Plan (planeje, com revisão humana obrigatória) → Agent (execute com contexto estruturado). Para edits pontuais, Edit Mode ou Inline Chat (Ctrl+I) são mais eficientes.

Seta 1 — Ask. Seta 2 — [Explore como estratégia, não modo oficial; veja nota]. Seta 3 — Agent, o modo central para SDD. Seta 4 — Plan, essential para human-in-the-loop. Fechamento: o fluxo Plan → Agent é o coração do SDD com Copilot Chat.

03 / GitHub Copilot Chat — Features

Features Principais

Participantes (@)

  • @workspace — contexto do projeto inteiro
  • @vscode — comandos e settings do editor
  • @terminal — ajuda no terminal
  • @github — PRs, issues, busca web

Slash Commands (/)

  • /explain — explica o código selecionado
  • /fix — corrige bugs automaticamente
  • /tests — gera testes unitários
  • /doc — documenta funções e APIs

Chat Variables (#)

  • #file — anexa arquivo como contexto
  • #web — busca na web em tempo real
  • #selection — foca no trecho selecionado
  • #codebase — indexa o workspace inteiro

MCP Integration

Model Context Protocol — padrão aberto para conectar Copilot a ferramentas externas: bancos de dados, APIs, serviços cloud. GitHub MCP Server já disponível.

Suporte a Imagens

Anexe screenshots (JPEG, PNG, GIF, WEBP) — descreva UIs, explique diagramas de arquitetura ou analise erros visuais com modelos multimodais.

Inline Chat

Ctrl+I diretamente no editor — edite código sem abrir o painel lateral. Refatore qualquer seleção com texto natural.

Copilot Memory

Memória persistente entre sessões — o Copilot lembra preferências, padrões de código e contexto do projeto. Enquanto AGENTS.md é contexto estático, Memory é contexto dinâmico aprendido. (Public Preview, GitHub.com)

Copilot Spaces

Espaços temáticos de conhecimento — concentre docs, PRDs, specs e guias em um repositório curado de contexto para o agente. Diretamente alinhado com SDD: um Copilot Space pode ser o "repositório de specs" do time.

Organizo por categoria para facilitar memorização: participantes com @, slash commands com /, variáveis de chat com # e integrações (MCP, multimodal, inline).

Qualidade de resposta depende diretamente de qualidade de contexto. Usar @workspace + #file:PRD.md é significativamente mais eficaz do que abrir o chat sem contexto explícito. A combinação de contexto de workspace com arquivo específico é o padrão recomendado para SDD.

Disponibilidade de cada recurso pode variar por interface — IDE, github.com, mobile. Verifiquem no ambiente de uso.

GitHub Copilot CLI

GA (25/02/2026) Terminal-first SDD-ready

O Copilot CLI leva a experiência do GitHub Copilot para o terminal, complementando o Chat da IDE com execução orientada por linguagem natural no shell.

A CLI está em GA desde 25/02/2026, disponível para todos os planos Copilot — incluindo Free. Para Business e Enterprise, admins habilitam por política, o que abre métricas de uso no nível da organização, anunciadas em 27/02/2026.

Governança operacional: autonomia com responsabilidade. A sequência no terminal segue a mesma lógica do spec-kit — plan → aprovar → executar → revisar diff → commit. Nunca commitar sem inspecionar o que foi gerado.

Human-in-the-loop no terminal é tão importante quanto na IDE. Use aprovações, políticas e hooks para bloquear comandos inseguros antes da execução. O modelo pode sugerir comandos tecnicamente corretos que são contextualmente errados para o seu ambiente.

Novidades de navegação (Abr/2026): Plan Mode (Shift+Tab) — alterna entre modo de planejamento e modo de execução sem iniciar nova sessão; flag -p / --prompt — permite passar o prompt diretamente na linha de comando, ideal para scripts e automações CI/CD (copilot -p "explain this error").

03 / GitHub Copilot — Agent Skills

Agent Skills — Dez/2025

O GitHub Copilot suporta nativamente Agent Skills — diretórios com um arquivo SKILL.md como entrypoint, seguindo o padrão aberto agentskills.io introduzido pela Anthropic para o Claude Code e adotado pelo GitHub em Dez/2025.

  • Padrão aberto: agentskills.io — especificação de diretórios com SKILL.md
  • Auto-descoberta: Copilot varre .github/skills/ automaticamente
  • Progressive Disclosure: descrição sempre no contexto; skill completa carregada sob demanda
  • Portabilidade: mesmo padrão funciona no Claude Code, Cursor, Gemini CLI e outros agentes
  • VS Code: crie Skills pelo chat — "@copilot create a skill for React patterns"

Estrutura de uma Skill

.github/
└── skills/
    └── react-patterns/
        ├── SKILL.md        ← entrypoint
        ├── hooks.md
        └── examples/

SKILL.md — Entrypoint

---
name: react-patterns
description: Padrões de componentes React
  com hooks, Context API e performance.
---

Carregue esta skill ao trabalhar
com componentes React. Inclui:
hooks, Context, memo, lazy.

Agent Skills são modularização de conhecimento especializado: você não injeta todo o contexto de uma vez, injeta o que é relevante para a tarefa atual.

Com SKILL.md como entrypoint e carregamento sob demanda, o agente mantém foco e não gasta tokens em contexto que não contribui para a tarefa presente. Isso se alinha diretamente com Progressive Disclosure — que veremos na seção seguinte.

Ponto importante: Agent Skills entrou em GA no GitHub Copilot em 18/12/2025. O mesmo padrão agentskills.io funciona em Claude Code, Cursor e Gemini CLI — o investimento em criar Skills é portável entre ferramentas.

Seta 1 — padrão aberto agentskills.io. Seta 2 — auto-descoberta em .github/skills/. Seta 3 — carregamento sob demanda (Progressive Disclosure). Seta 4 — portabilidade entre agentes. Seta 5 — criação via VS Code Chat. Seta 6 — estrutura do SKILL.md. Fechamento: Skills como unidade de especialização modular — menos ruído, mais foco por tarefa.

03 / GitHub Copilot Chat — SDD

GitHub Copilot + SDD = 🚀

A spec é o prompt perfeito. Quando você dá ao GitHub Copilot um PRD.md bem estruturado + AGENTS.md, ele tem todo o contexto necessário para entregar exatamente o que você precisa.
  • PRD.md como contexto principal via #file
  • AGENTS.md carregado automaticamente no Agent Mode
  • Agent Mode executa RF por RF com rastreabilidade
  • Plan Mode cria o plano de implementação para revisão humana
  • Iteração guiada pelos critérios de aceite (CA) do PRD

Prompt SDD Ideal

@workspace Com base em:
- #file:PRD.md (requisitos)
- #file:AGENTS.md (contexto)

Implemente o RF01 seguindo
exatamente os critérios de aceite
CA01 e CA02. Escreva testes para
cobrir os dois cenários descritos.
🎯 SDD transforma prompts vagos em instruções precisas e o GitHub Copilot em um colaborador previsível.

Fecho essa seção com um prompt orientado por artefato — porque ele traduz bem o espírito de SDD na prática. Com PRD e AGENTS no contexto, o pedido pode ser curto e objetivo: implementar um RF específico com critérios de aceite explicitamente testados.

A saída esperada deixa de ser "qualquer código" e passa a ser entrega verificável. A combinação de @workspace + #file:PRD.md + #file:AGENTS.md é o padrão canônico de trabalho com SDD no Copilot.

Seta 1 — PRD como contexto principal via #file. Seta 2 — AGENTS carregado automaticamente ou via #file. Seta 3 — Agent Mode executa RF por RF com rastreabilidade. 03-F / Codex — Segurança

Sandbox, Approvals e Confiança

Sandbox

  • read-only: inspeção sem mutação.
  • workspace-write: edição dentro do workspace.
  • danger-full-access: só em ambiente isolado.

Approvals

  • on-request: pede aprovação para sair do sandbox.
  • never: não pausa para pedir aprovação.
  • untrusted: exige aprovação para mutações.
Autonomia sem limite vira risco. O harness correto define onde o agente pode ler, escrever e executar. 
# Preset prático para trabalho local
codex --full-auto

# Equivale a:
# --sandbox workspace-write
# --ask-for-approval on-request
Nota de atualização: Codex evolui em ritmo acelerado. Esta palestra deve ser revisada mensalmente e os detalhes de sandbox/approvals precisam ser conferidos na documentação oficial antes de cada apresentação.

Sandbox e approvals são parte do harness. Eles não substituem testes e revisão, mas definem limites operacionais para a autonomia do agente.

Em ambientes governados, a pergunta não é "o agente consegue?". A pergunta é: "o agente consegue dentro de um perímetro seguro, auditável e reversível?".

Como Codex recebe atualizações frequentes, trate este slide como snapshot operacional. Antes de cada palestra, valide comandos, presets, nomes de policies e comportamento atual de approvals na documentação oficial. A proposta é revisar esta palestra mensalmente para acompanhar esse ritmo.

03-G / Codex — Comandos

Comandos Codex no Fluxo SDD

Preparar contexto

  • /init: cria base de AGENTS.md.
  • /mention: destaca specs, PRDs e arquivos-chave.
  • /status: confere modelo, política, writable roots e tokens.

Controlar entrega

  • /permissions: ajusta autonomia e approvals.
  • /compact: resume histórico e libera contexto.
  • /diff + /review: revisa mudança antes do PR.
Leitura SDD: comandos não substituem especificação. Eles ajudam a apontar contexto, limitar autonomia, revisar evidências e manter a conversa enxuta.

Não vale transformar este ponto em manual de CLI. A curadoria é intencional: só entram comandos que ajudam o fluxo SDD.

Dados verificados para a edição Maio/2026 na documentação oficial de slash commands do Codex CLI. Antes de reapresentar, conferir se nomes e comportamento continuam iguais.

Conexão pedagógica: /init ajuda a criar instruções persistentes, /mention reduz ambiguidade, /permissions controla risco, /compact conversa com economia de contexto, /diff e /review fecham o ciclo de validação.

03-H / Codex — Automação

codex exec e Automação SDD

codex exec é o modo não interativo do Codex para scripts, CI/CD e tarefas repetíveis. Em SDD, ele só deve entrar quando a spec, os limites e a validação já estão claros.

  • --full-auto: permite edição no workspace com baixo atrito.
  • --json: emite eventos JSONL para automações.
  • --output-last-message: salva a resposta final.
  • --output-schema: valida saída estruturada.
  • Prompts, logs e tool output podem conter dados sensíveis.

Exemplo seguro

codex exec --full-auto \
  --json \
  --output-last-message resumo.md \
  "Leia o PRD.md, implemente apenas
   o RF01, rode os testes e pare."
Evite danger-full-access fora de runners isolados. Automação boa começa com escopo pequeno e checks objetivos.

Esse é o ponto onde SDD encontra automação de verdade. Se o requisito está claro e o harness valida o resultado, uma tarefa pode ser executada de forma não interativa.

Mas a condição é importante: não automatize ambiguidade. Automatize tarefas pequenas, bem especificadas e com critérios de aceite objetivos.
