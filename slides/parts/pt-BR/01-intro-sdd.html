Seção 01

SDD

Spec-Driven Development: A evolução do TDD e BDD na era da IA generativa

Vamos começar pelo fundamento: o que é SDD e por que ele ficou tão relevante agora que temos agentes com execução multi-etapas.

A pergunta central não é mais "a IA consegue fazer isso?" — já ficou claro que consegue. A pergunta agora é: "como faço para que a IA faça isso de forma previsível e repetível?" SDD responde essa segunda pergunta.

01 / O que é SDD?

SDD — Spec-Driven Development

Uma abordagem de desenvolvimento onde especificações estruturadas (specs) são o artefato primário, guiando AI agents para gerar código de forma consistente e reduz alucinações, com o humano no centro do processo.

  • Spec-First: a spec é escrita antes do código
  • Human-in-the-Loop: validação humana em cada etapa
  • Contexto estruturado: PRD, AGENTS, Rules e Skills
  • Rastreabilidade: cada decisão tem origem em uma spec

Analogia

Assim como um arquiteto precisa de plantas antes de construir, um AI agent precisa de specs antes de codificar.

Analogia didática: SDD ≈ TDD, mas para especificações, não testes. A spec guia a implementação, não o contrário.

SDD não elimina TDD/BDD: SDD define o "o quê" e "por quê"; testes validam o "funciona".

↓ pressione ↓ para continuar nesta seção

Quando eu falo em SDD, estou falando de tratar especificação como artefato executável de engenharia — não como documentação decorativa que envelhece em uma pasta.

A analogia da planta continua sendo a mais direta: sem planta, a construção sai no improviso. Com IA é igual — o humano define intenção, limite e critério de aceite; o agente executa dentro desse contrato. Sem esse contrato, cada sessão começa quase do zero.

Reforço: SDD complementa testes, code review e segurança — ele não os substitui. Isso fica claro no próximo slide.

Seta 1 — Spec-First: a especificação existe antes do código. Seta 2 — Human-in-the-Loop: validação humana em cada etapa crítica. Seta 3 — Contexto Estruturado: as quatro camadas que veremos em detalhes. Seta 4 — Rastreabilidade: cada decisão rastreável até uma spec aprovada. Fechamento: previsibilidade é consequência direta da qualidade da especificação.

01 / SDD — Benefícios

Por que Adotar SDD?

Previsibilidade

O agente segue a spec, eliminando surpresas e desvios de requisitos durante a implementação.

Reduz Alucinações

Contexto estruturado reduz drasticamente as alucinações do modelo de linguagem.

Documentação Viva

O PRD.md evolui junto com o projeto, sempre refletindo o estado atual do produto.

Rastreabilidade

Cada decisão técnica tem origem rastreável em uma spec aprovada pelo time.

Velocidade

Menos ciclos de revisão = implementações mais rápidas e com menor custo de mudança.

Comunicação

Specs alinham desenvolvedores, PMs e stakeholders em uma única fonte de verdade.

Esses benefícios aparecem no dia a dia de engenharia: menos loop de correção tardia, menos perda de contexto entre sessões e melhor alinhamento entre dev, produto e arquitetura.

Velocidade aqui não vem de "pular etapa". Vem de ter menos retrabalho porque a intenção ficou clara desde o início. Cada card responde uma dor real de time — pergunte à audiência qual delas ressoa mais no contexto deles.

Setas 1 a 6: Previsibilidade → Reduz Alucinações → Documentação Viva → Rastreabilidade → Velocidade → Comunicação. Fechamento: conectar velocidade com redução de retrabalho, não com celeridade imprudente.

01 / SDD — Limites e Riscos

SDD reduz ambiguidade, mas não substitui:

  • Testes automatizados
  • Code review
  • Threat modeling / security review
  • Evals (nem que seja checklist qualitativa)
🎯 SDD aumenta previsibilidade. Qualidade final ainda depende de validação técnica contínua.

Este slide existe para manter o pé no chão: SDD não substitui disciplina de engenharia. Testes automatizados, code review, segurança e evals continuam obrigatórios.

Sem essas práticas, SDD apenas acelera o erro com mais eficiência. A metáfora que uso: você pode construir mais rápido com plantas melhores, mas ainda precisa de inspetor de obra.

Setas 1 a 4: Testes → Code Review → Threat modeling/segurança → Evals. Fechamento: sem validação contínua, a IA só acelera erro — com validação, a IA amplifica qualidade.

01 / Por que SDD hoje?

O Contexto de 2025/2026

Vivemos a era dos AI Coding Agents. GitHub Copilot, Codex, Cursor, Gemini CLI, Claude Code... Enfim, o desenvolvimento nunca foi tão rápido, tão autônomo e tão sensível à qualidade do contexto.
  • Modelos geram código em segundos, mas sem contexto estruturado
  • Quanto maior o contexto, maior a chance de alucinação
  • Ciclos de revisão multiplicam o custo de desenvolvimento
  • Retrabalho consome até 30–40% do tempo dos times (ref. surveys de produtividade de eng. de software)

Problema Central

Os AI agents são poderosos, mas precisam de contexto estruturado para produzir resultados consistentes.

SDD é a Resposta

Specs funcionam como um "contrato" entre o desenvolvedor e a IA.

O cenário atual é este: agentes como GitHub Copilot, Codex, Cursor e Claude Code estão muito mais capazes — execução multi-etapas, acesso a terminal, arquivos e ferramentas externas. Mas essa capacidade ampliada não resolve contexto mal definido. Na verdade, mais autonomia com contexto ruim amplifica o custo do erro.

Sobre o dado "30-40% de retrabalho" no slide: é uma estimativa que circula em surveys de produtividade de engenharia de software, mas sem uma fonte primária universal única. Use como referência de ordem de magnitude — o ponto correto é que retrabalho por contexto mal definido é caro e mensurável. Meçam no próprio time.

Seta 1 — código rápido sem contexto estruturado. Seta 2 — mais capacidade com contexto ruim amplifica alucinação. Seta 3 — ciclos de revisão têm custo crescente. Seta 4 — retrabalho como fato econômico do time. Fechamento: SDD entra para resolver especificamente esse gap de contexto — não é complexidade extra, é redução de variabilidade.

01 / Por que SDD hoje? — Princípios

SDD como Resposta para a IA

Spec-First

A especificação é o artefato de maior valor. Código, testes e docs são derivados da spec, não o contrário.

Human-in-the-Loop

O humano revisa e aprova cada spec antes que o agente implemente. A IA executa, o humano decide.

Architecture-First

"Spec-first" é o análogo de "Architecture-first" para sistemas de IA. A estrutura guia a construção.

Rastreabilidade

Cada linha de código pode ser rastreada até um requisito aprovado. Auditoria e rollback ficam triviais.

💬 "Não deixe a IA improvisar. Dê a ela uma spec bem escrita e ela entregará exatamente o que você precisa."

Fechando a seção de fundamentos: spec-first, human-in-the-loop, architecture-first e rastreabilidade. Esses quatro pilares importam principalmente em contextos com exigência de compliance e auditoria, porque cada decisão passa a ter origem explícita e verificável.

A citação no highlight-box resume bem a prática: "Não deixe a IA improvisar. Dê a ela uma spec bem escrita e ela entregará exatamente o que você precisa."
