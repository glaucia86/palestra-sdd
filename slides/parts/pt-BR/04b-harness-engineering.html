06 / Harness Engineering: O que é?

Agent = Model + Harness

O modelo é o cérebro.
O harness é tudo o que o rodeia.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering projeta instruções, tools, ambiente, estado, feedback e observabilidade para tornar o trabalho do agente confiável.

  • É um subconjunto de Context Engineering: foco no sistema operacional do agente, não só no prompt
  • O problema que resolve: dois agentes com o mesmo modelo e mesma tarefa produzem resultados radicalmente diferentes. A diferença está no harness
  • Vocabulário emergente: HumanLayer, Martin Fowler, OpenAI e Walking Labs oferecem perspectivas complementares

Fórmula 1

O modelo é o piloto talentoso, mas limitado sem suporte. O harness é a pista + pit crew + telemetria: quem viabiliza a volta rápida com segurança.

Trocar o piloto por outro mais rápido raramente resolve o problema. Geralmente o gargalo está no harness.

Harness Engineering = cuidar do pit crew com o mesmo rigor que você cuida do piloto

Técnica: Agent = Model + Harness separa capacidade do modelo do sistema que fornece instruções, tools, ambiente, estado, feedback e observabilidade.

Impacto executivo: antes de pagar por mais capacidade, a equipe pode localizar a camada que limita a execução confiável.

Controle e KPI: acompanhe first-pass acceptance, regressões, retries e tempo de review por configuração de harness.

Caveat: a analogia da Fórmula 1 é didática; falhas podem estar no modelo ou no harness e precisam de evidência para atribuição.

Técnica: o diagrama separa o harness em cinco subsistemas fora dos pesos do modelo: estado, instruções, ferramentas, feedback e ambiente.

Impacto executivo: a decomposição transforma uma discussão abstrata sobre qualidade do agente em pontos concretos de investimento e diagnóstico.

Controle e KPI: priorize feedback porque testes, lint e build fecham o loop de verificação autônoma; acompanhe falhas e retries por subsistema.

Caveat: os cinco blocos são uma síntese didática. Observabilidade atravessa estado e feedback, e as fronteiras podem variar conforme a plataforma.

06 / Harness Engineering: Framework

Guides & Sensors

Framework de Martin Fowler: feedforward (antes) + feedback (depois)

Guides (feedforward)

Dirigem o agente ANTES de ele agir e aumentam a probabilidade de acertar na primeira tentativa

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, exemplos few-shot, contexto semântico

Sensors (feedback)

Observam APÓS o agente agir, detectam problemas e permitem auto-correção de curso

Computational
Testes, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, agente de code review, análise semântica

GPS = Guide feedforward
te diz onde virar antes da curva

Câmera de velocidade = Sensor feedback
detecta o erro depois que aconteceu

Guides previnem; Sensors comprovam e corrigem.

Regra objetiva: checker determinístico primeiro.
Julgamento inferencial: seletivo; nunca é o único oracle.

Técnica: Guides atuam antes; Sensors observam depois. Ambos podem ser computacionais ou inferenciais.

Impacto executivo: prevenção reduz retrabalho, enquanto feedback produz evidência para corrigir e governar a execução.

Controle e KPI: para regra objetiva, execute teste, lint ou typecheck antes de qualquer julgamento semântico; meça cobertura e falsos positivos.

Caveat: sensor inferencial é probabilístico e seletivo; não substitui um oracle determinístico quando a regra pode ser executada.

06 / Harness Engineering: Operacionalização

O Harness que Escala

Não é “um prompt melhor”. É um sistema operacional enxuto para agentes trabalharem com evidência.

Repo como fonte

Conhecimento crítico precisa estar no repositório: arquitetura, comandos, restrições e decisões.

Agent Skills

AGENTS.md roteia; SKILL.md carrega conhecimento especializado sob demanda.

Maker / Checker

Mudança de alto risco separa quem produz de quem verifica critérios e evidência.

WIP = 1

Uma unidade ativa por vez, com critério de aceite e evidência executável de conclusão.

State + Observabilidade

Estado, logs, traces, checks e histórico tornam progresso e falha auditáveis.

Limites ≠ Prova

Sandbox e approvals limitam ação; testes e review comprovam o resultado.

Falha recorrente: atribua a instrução, tool, ambiente, state, feedback ou observabilidade antes de trocar o modelo.

Técnica: maker/checker, WIP limitado, state e observabilidade reduzem erro correlacionado, dispersão e perda de continuidade.

Impacto executivo: cada unidade termina com evidência revisável, responsável claro e blast radius controlado.

Controle e KPI: acompanhe WIP, checks por slice, retomadas sem rediscovery, regressões e falhas por camada do harness.

Caveat: sandbox e approvals reduzem capacidade de dano, mas não demonstram correção; testes e review continuam necessários.

06 / Harness Engineering: Ponte temporal

Handoff preserva. Harness executa. Loop reconcilia.

Cada camada responde uma pergunta diferente e entrega estado para a próxima.

SDD

Intenção

contrato + critérios

Slice

Unidade

escopo + evidência

Handoff

Continuidade

state + owner

Harness

Execução

guides + checks

Loop

Tempo

repetir · parar · escalar

Dimensão temporal: quem dispara, como progride, o que sobrevive entre runs e quando deve parar.
Agora deixamos de projetar apenas o ambiente e passamos a projetar o sistema que o aciona.

Técnica: SDD define o contrato, a Slice limita o trabalho, o Handoff preserva state, o Harness oferece execução e sinais; Loop Engineering adiciona trigger, progressão e parada.

Impacto executivo: a cadeia separa intenção, responsabilidade, evidência e automação sem esconder o gate humano.

Controle e KPI: cada transição deve produzir owner, terminal state e evidência; meça outcomes aceitos, retries e tempo de retomada.

Caveat: esta é uma ponte narrativa. A próxima seção apresentará Loop Engineering como termo emergente, não como padrão formal consolidado.
