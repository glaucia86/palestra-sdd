Agent = Model + Harness

Fechando o loop entre spec e gate de produção

Chegamos ao bloco mais emergente da palestra — um tema que está ganhando força agora, em 2026, à medida que equipes escalam o uso de agentes autônomos e precisam responder: como garantir que o código gerado automaticamente é seguro, correto e alinhado com a spec?

O termo "Harness Engineering" foi cunhado por Viv (HumanLayer, 2025) e ganhou tração com o artigo de Martin Fowler e o experimento de escala da OpenAI com o Codex. A ideia central é simples: se o agente é a soma do modelo mais tudo que o rodeia, então "Harness Engineering" é a prática de cuidar desse "tudo que rodeia" com o mesmo rigor que você cuida do código de produção.

Apresente isso como uma extensão natural de SDD — não como um novo framework a aprender do zero.

06 / Harness Engineering: O que é?

Agent = Model + Harness

O modelo é o cérebro.
O harness é tudo o que o rodeia.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering é a prática de projetar instruções, ferramentas, ambiente, estado e feedback para tornar o trabalho do agente confiável.

  • É um subconjunto de Context Engineering: foco no sistema operacional do agente, não só no prompt
  • O problema que resolve: dois agentes com o mesmo modelo e mesma tarefa produzem resultados radicalmente diferentes. A diferença está no harness
  • Proposto por Viv (HumanLayer) · documentado por Martin Fowler · popularizado pelo experimento de escala da OpenAI
🏎️

Fórmula 1

O modelo é o piloto talentoso, mas limitado sem suporte. O harness é a pista + pit crew + telemetria: quem viabiliza a volta rápida com segurança.

Trocar o piloto por outro mais rápido raramente resolve o problema. Geralmente o gargalo está no harness.

Harness Engineering = cuidar do pit crew com o mesmo rigor que você cuida do piloto

A equação "Agent = Model + Harness" vem do blog da HumanLayer (Viv, 2025) e é a forma mais compacta de explicar por que trocar o modelo raramente é a resposta certa para problemas de qualidade do agente. Na maioria dos casos, o problema está no harness — na qualidade das instruções, no contexto fornecido, nos mecanismos de feedback.

O learning da Walking Labs reforça uma visão mais operacional: Harness não é um arquivo de prompt. É o conjunto de instruções, ferramentas, ambiente, estado persistente e feedback que determina quanto da capacidade do modelo vira execução confiável.

Context Engineering é o termo mais amplo — Harness Engineering é um subconjunto com foco específico no sistema que rodeia o agente: o que ele recebe antes de agir (guides), o que pode executar, como preserva estado e o que verifica depois (sensors).

Analogia da Fórmula 1: funciona bem para públicos gerais. Piloto = modelo. Pista/pit crew/telemetria = harness. Trocar o piloto por Hamilton não adianta se o carro não está calibrado. O trabalho real é no harness.

06 / Harness Engineering: Framework

Guides & Sensors

Framework de Martin Fowler: feedforward (antes) + feedback (depois)

Guides (feedforward)

Dirigem o agente ANTES de ele agir e aumentam a probabilidade de acertar na primeira tentativa

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, exemplos few-shot, contexto semântico

Sensors (feedback)

Observam APÓS o agente agir, detectam problemas e permitem auto-correção de curso

Computational
Testes, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, agente de code review, análise semântica

GPS = Guide feedforward
te diz onde virar antes da curva

Câmera de velocidade = Sensor feedback
detecta o erro depois que aconteceu

Bons harnesses combinam os dois, mas preferem Guides.

Computational = determinístico, rápido, executa sempre.
Inferential = semântico, caro, executa seletivamente.

O framework de Martin Fowler (artigo harness-engineering.html, 2025) divide os mecanismos do harness em dois eixos: como agem (feedforward = Guides; feedback = Sensors) e como são implementados (Computational = determinístico; Inferential = IA).

A intuição-chave: Guides são mais baratos que Sensors porque evitam o erro antes que ele aconteça. Um AGENTS.md bem escrito (Guide Computational) é infinitamente mais barato que um agente de code review (Sensor Inferential) rodando em cada commit. Invista primeiro nos Guides.

Computational vs Inferential: testes passam ou falham — isso é Computational. Um LLM julgando se o código está correto semanticamente — isso é Inferential. Inferential dá mais cobertura mas é mais caro e não-determinístico. Use para coisas que testes não conseguem capturar.

A analogia GPS + câmera funciona bem: GPS é feedforward (te guia antes), câmera é feedback (te pune depois). Sistemas maduros combinam os dois, mas preferem Guides — porque prevenir é mais barato que detectar.

06 / Harness Engineering: Operacionalização

O Harness que Escala

Não é “um prompt melhor”. É um sistema operacional enxuto para agentes trabalharem com evidência.

Repo como fonte

Conhecimento crítico precisa estar no repositório: arquitetura, comandos, restrições e decisões.

Arquivos roteadores

AGENTS.md aponta o caminho. Detalhes vivem em docs/skills sob demanda.

Inicialização

Antes de codar: ambiente roda, testes executam, tarefa está quebrada em passos verificáveis.

WIP = 1

Uma unidade ativa por vez, com critério de aceite e evidência executável de conclusão.

Observabilidade

Logs, traces, checks, rubricas e histórico tornam o “parece certo” auditável.

Saída limpa

Sessão só termina com build/testes, progresso, artefatos e próximo passo em estado claro.

Regra prática: quando o agente falhar, investigue primeiro o harness: tarefa vaga, contexto invisível, ambiente quebrado, falta de feedback ou estado perdido.

Este slide sintetiza o learning da Walking Labs. A ideia importante: Harness Engineering não é só prompt ou AGENTS.md. É o sistema operacional do agente.

Repo como fonte: para o agente, o que não está no repositório praticamente não existe. Arquivos roteadores: AGENTS.md deve ser curto, apontando para documentação especializada conforme a tarefa — isso conversa diretamente com Progressive Disclosure.

Inicialização: separar setup de implementação evita que a primeira sessão misture fundação e feature. WIP=1 reduz overreach: o agente para de abrir cinco frentes e passa a terminar uma unidade verificável.

Observabilidade transforma revisão subjetiva em evidência: logs, traces, testes, rubricas e critérios de aceite. Saída limpa fecha o ciclo: build/testes/progresso/artefatos precisam estar em ordem para a próxima sessão não recomeçar do zero.

Fechamento: quando o agente falha, não troque de modelo como primeira reação. Atribua a falha a uma camada do harness e corrija essa camada.

06 / Harness Engineering: Conexão com SDD

SDD + Harness = Ciclo Fechado

Seus artefatos SDD já são componentes de harness. O que falta é dar nome a cada um e usar com esse propósito em mente.

Artefato SDD Papel no Harness
spec.md / PRD.md Guide Computational: feedforward com intenção estruturada
AGENTS.md Guide Computational: regras e restrições para o agente
Critérios de Aceite (CA) Definem os targets dos Sensors: "passou = aderente à spec"
Testes (CI/CD) Sensor Computational: feedback determinístico
Skills.md Guide Inferential: contexto especializado sob demanda
Se você pratica SDD, você já está fazendo Harness Engineering.
Harness Engineering é o nome para o que você faz quando cuida dos artefatos SDD com rigor operacional.

O ciclo

① Spec (SDD) → Guide feedforward para o agente
② Agente gera → Sensor Computational avalia
③ Falhou → itera até os Sensors passarem
④ Passou → humano revisa resultado, não processo
Codex, da OpenAI (2025): "Our biggest challenges now center on designing environments, feedback loops, and control systems". Resultado: 1 milhão de linhas de código com zero linhas escritas manualmente.

A tabela é a ponte entre o que o público já conhece (artefatos SDD) e o novo vocabulário (Guides/Sensors). Não é preciso reaprender nada — é reconhecer o que já fazem com o nome correto e o framework explícito.

O ponto sobre AGENTS.md ser Guide mas não Sensor é importante: AGENTS.md com DON'T é instrução, não enforcement. O enforcement real vem de hooks, CI e políticas — esses são os Sensors Computacionais. SDD + CI rigoroso = loop fechado sem precisar de revisor humano em cada commit.

A quote da OpenAI é poderosa: o time de Codex (2025) relatou 1 milhão de linhas de código com zero intervenção manual — o que eles descrevem como o maior desafio não foi o modelo, mas "designing environments, feedback loops, and control systems". Isso é a definição operacional de Harness Engineering.

Mensagem para fechar a seção: você não precisa implementar um "Harness Engineering framework" do zero — você já tem os componentes. O que falta é conectar a spec aos testes (targets dos Sensors) de forma explícita e automatizada.
