07 / Loop Engineering: Evolução

O prompt permanece. A operação muda.

Antes · scheduler humano

Prompt Engineering manual

humano escreve agente responde

O humano agenda retries, recompõe contexto e integra cada resposta.

Depois · loop delimitado

Goal + state + feedback

goal / spec loop bounded terminal state

O sistema observa, age e verifica; o humano define direção, orçamento e gates.

Não é “prompt morreu”. O prompt vira uma peça dentro de um sistema com memória, feedback e condição de parada.

Técnica: o loop conserva prompts, mas automatiza progressão, observação e retry dentro de limites explícitos.

Impacto executivo: atenção humana migra de coordenação mecânica para produto, risco e aceitação.

Controle e KPI: compare tempo humano de operação, retries e outcomes aceitos antes e depois.

Fonte/caveat: síntese editorial baseada em LangChain e OpenAI Harness Engineering, consultados em julho de 2026; nem toda tarefa justifica automação recorrente.

Transição: para automatizar sem perder controle, precisamos nomear os blocos do sistema.

07 / Loop Engineering: Blocos

Cinco blocos em execução. State entre runs.

1

evento, agenda ou comando autorizado

2

Observer

repo e sinais em worktree isolada

3

4

ações permitidas por escopo

5

Verifier

checks, maker/checker e revisão

State / memória operacionalgoal · decisões · evidência · orçamento consumido · próxima ação · terminal state
sobrevive à sessão

Sem state confiável, cada run recomeça do zero — e “autonomia” vira rediscovery caro.

Técnica: trigger inicia; observer lê sinais; skills fornecem contexto; tools executam; verifier julga evidência; state preserva continuidade.

Impacto executivo: componentes separados permitem localizar custo, falha e responsabilidade sem culpar genericamente o modelo.

Controle e KPI: registre run ID, owner, orçamento consumido, checks, decisão e próximo estado.

Fonte/caveat: síntese editorial baseada em LangChain, OpenAI Harness Engineering e padrões de agentes; a composição concreta varia por produto.

Transição: esse desenho lembra um control plane — com uma diferença decisiva.

Pense em reconciliação, não em autopilot

A analogia para aqui: controllers tradicionais executam lógica previsível; modelos são probabilísticos e não determinísticos. Por isso o loop exige verificação, budgets e gates humanos.

Técnica: ambos partem de estado desejado, observam o atual, calculam um gap e reconciliam até uma condição de parada.

Impacto executivo: a metáfora desloca o foco de “dar comandos” para governar estado, evidência e exceções.

Controle e KPI: meça convergência, regressões por retry e escaladas para revisão humana.

Fonte/caveat: analogia editorial de control loops; LLMs são probabilísticos, portanto a equivalência com Kubernetes não é operacional nem determinística.

07 / Loop Engineering: Níveis

Loops diferem pelo mecanismo e pela cadência

Mecanismo · LangChain

  • Agent loop: planejar → agir → observar
  • Verification loop: produzir → avaliar → corrigir
  • Event-driven: evento → run → sistema atualizado
  • Hill-climbing: traces → análise → harness melhorado

Cadência · produto

rápido agente codifica, testa e corrige médio developer revisa produto e direção lento feedback externo recalibra a spec
Responsabilidade não escala na mesma velocidade. O agente domina o loop rápido; pessoas e organização governam valor, feedback e risco.

Técnica: a taxonomia separa o que faz o loop avançar do tempo em que cada feedback chega.

Impacto executivo: automatizar o ciclo interno não remove discovery, direção de produto nem accountability.

Controle e KPI: escolha métricas por nível: checks no loop rápido, aceitação no developer loop e outcome no feedback externo.

Fonte/caveat: mecanismos publicados por LangChain em 2026; as três cadências são uma leitura editorial para esta palestra, não taxonomia normativa.

Transição: os casos mostram combinações diferentes desses mecanismos — e também seus custos.

Resultados publicados. Leitura editorial separada.

Bun · migração Zig → Rust

Publicado 1 milhão de linhas em menos de 2 semanas; suíte existente passou antes do merge.

Custo / risco ~US$ 165 mil em preço de API; regressões foram encontradas e corrigidas durante verificação.

Leitura editorial paralelismo só gera valor quando o verifier integra evidência.

LangChain · loops compostos

Publicado quatro mecanismos: agent, verification, event-driven e hill-climbing.

Leitura editorial loop externo melhora o harness; não prova que toda melhoria seja automática.

AutoResearch · experimento

Publicado agente altera train.py, mede val_bpb e registra resultados.

Leitura editorial objetivo mensurável e escopo estreito tornam o retry verificável.

Coding agents · PR

Publicado OpenAI descreve loops de revisão; GitHub limita cloud agents a draft PR e revisão humana.

Leitura editorial PR é envelope de handoff, não autorização para publicar.

Técnica: cada case explicita o dado publicado e a inferência usada na narrativa, evitando apresentar padrão como causalidade.

Impacto executivo: o case Bun evidencia simultaneamente velocidade, gasto de tokens/API e custo de verificação.

Controle e KPI: resultados dos cases não são metas transferíveis; meça custo e outcome aceito no próprio contexto.

Fonte/caveat: Anthropic, 16 jul. 2026; LangChain, 2026; karpathy/autoresearch; OpenAI Harness Engineering; GitHub Docs, consultados em julho de 2026. Os números pertencem ao case Bun.

Transição: casos de alto throughput tornam os limites de operação ainda mais importantes.

07 / Loop Engineering: Guardrails

Autonomia útil nasce de limites observáveis

Smart Zone

só automatize onde contexto e verificação sustentam a decisão

Context budget

budget de contexto, tempo, custo, iterações e paralelismo

Isolation

worktree, sandbox e permissões de menor privilégio

WIP = 1

uma unidade ativa por agente, com owner e evidência

Maker / Checker

produção e verificação independentes quando o risco pede

Human gate

narrativa, design, risco e publicação permanecem humanos

Sem retry infinito: falhou verificação, acabou budget ou faltou autorização → registre state e pare.

Técnica: Smart Zone, context budget, isolamento, WIP, maker/checker e human gate limitam blast radius e erro correlacionado.

Impacto executivo: parar de forma legível é um resultado válido quando continuar seria caro, inseguro ou não autorizado.

Controle e KPI: monitore budget exhaustion, blocked runs, unsafe actions evitadas, regressões e tempo até revisão.

Fonte/caveat: síntese de práticas do repositório, Anthropic, OpenAI e GitHub; sandbox limita ação, mas não comprova correção.

Técnica: content-refresh detecta claims voláteis, pesquisa fontes primárias, propõe slices, executa checks e termina em draft PR ou state de falha.

Impacto executivo: atualização recorrente fica auditável sem delegar à automação a responsabilidade editorial ou de publicação.

Controle e KPI: verificar fonte/data, context budget, rota principal, paridade PT/EN/ES, typecheck e build; falha produz handoff.

Transição: o loop termina onde começa a decisão responsável: revisão humana antes de qualquer merge, release ou deploy.
