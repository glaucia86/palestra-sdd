07 / Loop Engineering: Evolución

El prompt permanece. La operación cambia.

Antes · scheduler humano

Prompt Engineering manual

persona escribe agente responde

La persona programa retries, recompone contexto e integra cada respuesta.

Después · loop acotado

Goal + state + feedback

goal / spec loop acotado terminal state

El sistema observa, actúa y verifica; las personas definen dirección, presupuesto y gates.

No significa que “el prompt murió”. El prompt se convierte en una pieza dentro de un sistema con memoria, feedback y condición de parada.

Técnica: el loop conserva prompts, pero automatiza progresión, observación y retry dentro de límites explícitos.

Impacto ejecutivo: la atención humana pasa de la coordinación mecánica al producto, riesgo y aceptación.

Control y KPI: compare tiempo humano de operación, retries y outcomes aceptados antes y después.

Fuente/salvedad: síntesis editorial basada en LangChain y OpenAI Harness Engineering, consultados en julio de 2026; no toda tarea justifica automatización recurrente.

Transición: para automatizar sin perder control, necesitamos nombrar los bloques del sistema.

07 / Loop Engineering: Bloques

Cinco bloques en ejecución. State entre runs.

1

Trigger

evento, agenda o comando autorizado

2

Observer

repo y señales en una worktree aislada

3

Skills

contexto especializado bajo demanda

4

Tools

acciones permitidas por el alcance

5

Verifier

checks, maker/checker y revisión

State / memoria operativagoal · decisiones · evidencia · presupuesto consumido · próxima acción · terminal state
sobrevive a la sesión

Sin state confiable, cada run vuelve a empezar — y la “autonomía” se convierte en rediscovery costoso.

Técnica: trigger inicia; observer lee señales; skills aportan contexto; tools ejecutan; verifier juzga evidencia; state preserva continuidad.

Impacto ejecutivo: componentes separados permiten localizar costo, fallo y responsabilidad sin culpar genéricamente al modelo.

Control y KPI: registre run ID, owner, presupuesto consumido, checks, decisión y próximo estado.

Fuente/salvedad: síntesis editorial basada en LangChain, OpenAI Harness Engineering y patrones de agentes; la composición concreta varía por producto.

Transición: este diseño se parece a un control plane — con una diferencia decisiva.

07 / Loop Engineering: Control plane

Piense en reconciliación, no en autopilot

Control loopLoop Engineering
desired stategoal + spec + criterios

diffgap entre objetivo y evidencia

verifychecks + revisión + evals
reconcileretry acotado o terminal state

La analogía termina aquí: los controllers tradicionales ejecutan lógica previsible; los modelos son probabilísticos y no deterministas. Por eso el loop exige verificación, budgets y gates humanos.

Técnica: ambos parten de un estado deseado, observan el actual, calculan un gap y reconcilian hasta una condición de parada.

Impacto ejecutivo: la metáfora cambia el foco de “dar comandos” a gobernar state, evidencia y excepciones.

Control y KPI: mida convergencia, regresiones por retry y escaladas a revisión humana.

Fuente/salvedad: analogía editorial de control loops; los LLM son probabilísticos, por lo que la equivalencia con Kubernetes no es operativa ni determinista.

07 / Loop Engineering: Niveles

Los loops difieren por mecanismo y cadencia

Mecanismo · LangChain

  • Agent loop: planificar → actuar → observar
  • Verification loop: producir → evaluar → corregir
  • Event-driven: evento → run → sistema actualizado
  • Hill-climbing: traces → análisis → harness mejorado

Cadencia · producto

rápido el agente codifica, prueba y corrige medio developer revisa producto y dirección lento feedback externo recalibra la spec
La responsabilidad no escala a la misma velocidad. El agente domina el loop rápido; las personas y la organización gobiernan valor, feedback y riesgo.

Técnica: la taxonomía separa lo que hace avanzar el loop del tiempo en que llega cada señal de feedback.

Impacto ejecutivo: automatizar el ciclo interno no elimina discovery, dirección de producto ni accountability.

Control y KPI: elija métricas por nivel: checks en el loop rápido, aceptación en el developer loop y outcome en el feedback externo.

Fuente/salvedad: mecanismos publicados por LangChain en 2026; las tres cadencias son una lectura editorial para esta charla, no una taxonomía normativa.

Transición: los casos muestran combinaciones diferentes de estos mecanismos — y también sus costos.

07 / Loop Engineering: Casos

Resultados publicados. Lectura editorial separada.

Bun · migración Zig → Rust

Publicado 1 millón de líneas en menos de 2 semanas; la suite existente pasó antes del merge.

Costo / riesgo ~US$165 mil a precio de API; las regresiones se encontraron y corrigieron durante la verificación.

Lectura editorial el paralelismo solo genera valor cuando el verifier integra evidencia.

LangChain · loops compuestos

Publicado cuatro mecanismos: agent, verification, event-driven y hill-climbing.

Lectura editorial el loop externo mejora el harness; no prueba que toda mejora sea automática.

AutoResearch · experimento

Publicado el agente modifica train.py, mide val_bpb y registra resultados.

Lectura editorial un objetivo medible y un alcance estrecho hacen verificable el retry.

Coding agents · PR

Publicado OpenAI describe loops de revisión; GitHub limita cloud agents a draft PR y revisión humana.

Lectura editorial el PR es un envelope de handoff, no autorización para publicar.

Técnica: cada caso explicita el dato publicado y la inferencia usada en la narrativa, evitando presentar un patrón como causalidad.

Impacto ejecutivo: el caso Bun muestra a la vez velocidad, gasto de tokens/API y costo de verificación.

Control y KPI: los resultados de los casos no son metas transferibles; mida costo y outcome aceptado en su propio contexto.

Fuente/salvedad: Anthropic, 16 jul. 2026; LangChain, 2026; karpathy/autoresearch; OpenAI Harness Engineering; GitHub Docs, consultados en julio de 2026. Los números pertenecen al caso Bun.

Transición: los casos de alto throughput hacen aún más importantes los límites operativos.

07 / Loop Engineering: Guardrails

La autonomía útil nace de límites observables

Smart Zone

automatice solo donde contexto y verificación sostienen la decisión

Context budget

budget de contexto, tiempo, costo, iteraciones y paralelismo

Isolation

worktree, sandbox y permisos de mínimo privilegio

WIP = 1

una unidad activa por agente, con owner y evidencia

Maker / Checker

producción y verificación independientes cuando el riesgo lo exige

Human gate

narrativa, diseño, riesgo y publicación siguen siendo humanos

Sin retry infinito: falló la verificación, terminó el budget o falta autorización → registre state y deténgase.

Técnica: Smart Zone, context budget, aislamiento, WIP, maker/checker y human gate limitan blast radius y error correlacionado.

Impacto ejecutivo: detenerse de forma legible es un resultado válido cuando continuar sería costoso, inseguro o no autorizado.

Control y KPI: monitorice budget exhaustion, runs bloqueadas, acciones inseguras evitadas, regresiones y tiempo hasta revisión.

Fuente/salvedad: síntesis de prácticas del repositorio, Anthropic, OpenAI y GitHub; un sandbox limita acciones, pero no demuestra corrección.

Transición: apliquemos estos guardrails a un loop real de la propia charla.

Técnica: content-refresh detecta claims volátiles, investiga fuentes primarias, propone slices, ejecuta checks y termina en draft PR o estado explícito de fallo.

Impacto ejecutivo: la actualización recurrente queda auditable sin delegar a la automatización la responsabilidad editorial o de publicación.
