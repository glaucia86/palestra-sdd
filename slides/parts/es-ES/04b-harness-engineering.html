06 / Harness Engineering — ¿Qué es?

Agent = Model + Harness

El modelo es el cerebro.
El harness es todo lo que lo rodea.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering diseña instrucciones, tools, ambiente, estado, feedback y observabilidad para hacer confiable el trabajo del agente.

  • Es un subconjunto de Context Engineering: enfocado en el sistema operativo del agente, no solo en el prompt
  • El problema que resuelve: dos agentes con el mismo modelo y la misma tarea producen resultados radicalmente diferentes — la diferencia está en el harness
  • Vocabulario emergente: HumanLayer, Martin Fowler, OpenAI y Walking Labs ofrecen perspectivas complementarias

Fórmula 1

El modelo es el piloto — talentoso, pero limitado sin apoyo. El harness es la pista + pit crew + telemetría: lo que hace posible la vuelta rápida con seguridad.

Cambiar el piloto por uno más rápido raramente resuelve el problema — el cuello de botella suele estar en el harness.

Harness Engineering = cuidar del pit crew con el mismo rigor que cuidas del piloto

Técnica: Agent = Model + Harness separa la capacidad del modelo del sistema que aporta instrucciones, tools, ambiente, estado, feedback y observabilidad.

Impacto ejecutivo: antes de pagar por más capacidad, el equipo puede localizar la capa que limita la ejecución confiable.

Control y KPI: sigue la aceptación en el primer intento, regresiones, reintentos y tiempo de revisión por configuración de harness.

Salvedad: la analogía de Fórmula 1 es didáctica; los fallos pueden estar en el modelo o en el harness y requieren evidencia para atribuirlos.

06 / Harness Engineering — Framework

Guides & Sensors

Framework de Martin Fowler — feedforward (antes) + feedback (después)

Guides (feedforward)

Dirigen el agente ANTES de que actúe — aumentan la probabilidad de acertar a la primera

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, ejemplos few-shot, contexto semántico

Sensors (feedback)

Observan DESPUÉS de que el agente actúe — detectan problemas y permiten corrección de rumbo

Computational
Tests, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, agente code review, análisis semántico

GPS = Guide feedforward
te dice dónde girar antes de la curva

Cámara de velocidad = Sensor feedback
detecta el error después de que ocurrió

Guides previenen; Sensors demuestran y corrigen.

Regla objetiva: checker determinístico primero.
Juicio inferencial: selectivo; nunca es el único oracle.

Técnica: Guides actúan antes; Sensors observan después. Ambos pueden ser computacionales o inferenciales.

Impacto ejecutivo: la prevención reduce retrabajo, mientras el feedback produce evidencia para corregir y gobernar la ejecución.

Control y KPI: para una regla objetiva, ejecuta tests, lint o typecheck antes del juicio semántico; mide cobertura y falsos positivos.

Salvedad: un sensor inferencial es probabilístico y selectivo; no sustituye un oracle determinístico cuando la regla es ejecutable.

06 / Harness Engineering: Operacionalización

El Harness que Escala

No es “un prompt mejor”. Es un sistema operativo liviano para que agentes trabajen con evidencia.

Repo como fuente

El conocimiento crítico debe vivir en el repositorio: arquitectura, comandos, restricciones y decisiones.

Agent Skills

AGENTS.md enruta; SKILL.md carga conocimiento especializado bajo demanda.

Maker / Checker

Un cambio de alto riesgo separa quien produce de quien verifica criterios y evidencia.

WIP = 1

Una unidad activa por vez, con criterios de aceptación y evidencia ejecutable de conclusión.

Estado + Observabilidad

Estado, logs, traces, checks e historial vuelven auditables el progreso y los fallos.

Límites ≠ Prueba

Sandbox y approvals limitan acciones; tests y revisión demuestran el resultado.

Fallo recurrente: atribúyelo a instrucción, tool, ambiente, estado, feedback u observabilidad antes de cambiar el modelo.

Técnica: maker/checker, WIP limitado, estado y observabilidad reducen error correlacionado, dispersión y pérdida de continuidad.

Impacto ejecutivo: cada unidad termina con evidencia revisable, owner claro y blast radius controlado.

Control y KPI: sigue WIP, checks por slice, reanudaciones sin redescubrimiento, regresiones y fallos por capa del harness.

Salvedad: sandbox y approvals reducen la capacidad de daño, pero no demuestran corrección; tests y revisión siguen siendo necesarios.

06 / Harness Engineering — Puente temporal

Handoff preserva. Harness ejecuta. Loop reconcilia.

Cada capa responde una pregunta diferente y entrega estado a la siguiente.

SDD

Intención

contrato + criterios

Slice

Unidad

alcance + evidencia

Handoff

Continuidad

estado + owner

Harness

Ejecución

guides + checks

Loop

Tiempo

repetir · parar · escalar

Dimensión temporal: quién dispara, cómo progresa, qué sobrevive entre runs y cuándo debe parar.
Ahora dejamos de diseñar solo el ambiente y pasamos a diseñar el sistema que lo activa.

Técnica: SDD define el contrato, la Slice limita el trabajo, el Handoff preserva estado, el Harness aporta ejecución y señales; Loop Engineering añade trigger, progresión y parada.

Impacto ejecutivo: la cadena separa intención, responsabilidad, evidencia y automatización sin ocultar el gate humano.

Control y KPI: cada transición debe producir owner, estado terminal y evidencia; mide resultados aceptados, reintentos y tiempo de reanudación.

Salvedad: este es un puente narrativo. La próxima sección presenta Loop Engineering como término emergente, no como estándar formal consolidado.
