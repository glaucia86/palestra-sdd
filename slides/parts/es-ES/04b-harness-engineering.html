Llegamos al bloque más emergente de la charla — un tema que está ganando fuerza en 2026, a medida que los equipos escalan el uso de agentes autónomos y necesitan responder: ¿cómo garantizar que el código generado automáticamente es seguro, correcto y alineado con la spec?

El término "Harness Engineering" fue acuñado por Viv (HumanLayer, 2025) y ganó tracción con el artículo de Martin Fowler y el experimento de escala de OpenAI con Codex. Preséntalo como una extensión natural del SDD — no como un nuevo framework para aprender desde cero.

06 / Harness Engineering — ¿Qué es?

Agent = Model + Harness

El modelo es el cerebro.
El harness es todo lo que lo rodea.

system prompt · tools/MCPs · context · sub-agents · hooks

Harness Engineering es la práctica de diseñar instrucciones, herramientas, ambiente, estado y feedback para hacer confiable el trabajo del agente.

  • Es un subconjunto de Context Engineering: enfocado en el sistema operativo del agente, no solo en el prompt
  • El problema que resuelve: dos agentes con el mismo modelo y la misma tarea producen resultados radicalmente diferentes — la diferencia está en el harness
  • Acuñado por Viv (HumanLayer) · documentado por Martin Fowler · popularizado por el experimento de escala de OpenAI
🏎️

Fórmula 1

El modelo es el piloto — talentoso, pero limitado sin apoyo. El harness es la pista + pit crew + telemetría: lo que hace posible la vuelta rápida con seguridad.

Cambiar el piloto por uno más rápido raramente resuelve el problema — el cuello de botella suele estar en el harness.

Harness Engineering = cuidar del pit crew con el mismo rigor que cuidas del piloto

La ecuación "Agent = Model + Harness" viene del blog de HumanLayer (Viv, 2025). La diferencia de resultados entre dos agentes con el mismo modelo generalmente está en el harness — calidad de instrucciones, contexto provisto, mecanismos de feedback.

El learning de Walking Labs refuerza una visión operacional: Harness no es un archivo de prompt. Es el conjunto de instrucciones, herramientas, ambiente, estado persistente y feedback que determina cuánto de la capacidad del modelo se convierte en ejecución confiable.

Context Engineering es el término más amplio — Harness Engineering es un subconjunto enfocado en el sistema que rodea al agente: lo que recibe antes de actuar, lo que puede ejecutar, cómo preserva estado y qué lo verifica después.

06 / Harness Engineering — Framework

Guides & Sensors

Framework de Martin Fowler — feedforward (antes) + feedback (después)

Guides (feedforward)

Dirigen el agente ANTES de que actúe — aumentan la probabilidad de acertar a la primera

Computational
AGENTS.md, specs, rules, system prompt
Inferential
Skills, RAG, ejemplos few-shot, contexto semántico

Sensors (feedback)

Observan DESPUÉS de que el agente actúe — detectan problemas y permiten corrección de rumbo

Computational
Tests, linters, type checkers, CI/CD gates
Inferential
LLM-as-judge, agente code review, análisis semántico

GPS = Guide feedforward
te dice dónde girar antes de la curva

Cámara de velocidad = Sensor feedback
detecta el error después de que ocurrió

Los buenos harnesses combinan ambos, pero prefieren Guides.

Computational = determinístico, rápido, ejecuta siempre.
Inferential = semántico, costoso, ejecuta selectivamente.

Framework de Martin Fowler: Guides (feedforward, antes de actuar) y Sensors (feedback, después de actuar), cada uno Computational (determinístico) o Inferential (IA). Guides son más baratos que Sensors — prevenir es más barato que detectar.

06 / Harness Engineering: Operacionalización

El Harness que Escala

No es “un prompt mejor”. Es un sistema operativo liviano para que agentes trabajen con evidencia.

Repo como fuente

El conocimiento crítico debe vivir en el repositorio: arquitectura, comandos, restricciones y decisiones.

Archivos ruteadores

AGENTS.md apunta el camino. Los detalles viven en docs/skills bajo demanda.

Inicialización

Antes de codificar: ambiente corre, tests ejecutan y la tarea está dividida en pasos verificables.

WIP = 1

Una unidad activa por vez, con criterios de aceptación y evidencia ejecutable de conclusión.

Observabilidad

Logs, traces, checks, rúbricas e historial vuelven auditable el “parece correcto”.

Salida limpia

La sesión solo termina con build/tests, progreso, artefactos y próximo paso en estado claro.

Regla práctica: cuando el agente falla, investiga primero el harness: tarea vaga, contexto invisible, ambiente roto, falta de feedback o estado perdido.

Esta diapositiva sintetiza el learning de Walking Labs. La idea importante: Harness Engineering no es solo prompt o AGENTS.md. Es el sistema operativo del agente.

Repo como fuente: para el agente, lo que no está en el repositorio prácticamente no existe. Archivos ruteadores: AGENTS.md debe ser corto y apuntar a documentación especializada según la tarea — esto conversa directamente con Progressive Disclosure.

Inicialización separa setup de implementación. WIP=1 reduce overreach: el agente deja de abrir cinco frentes y termina una unidad verificable.

Observabilidad transforma revisión subjetiva en evidencia: logs, traces, tests, rúbricas y criterios de aceptación. Salida limpia cierra el ciclo.

06 / Harness Engineering — Conexión con SDD

SDD + Harness = Ciclo Cerrado

Tus artefactos SDD ya son componentes de harness — lo que falta es reconocerlos y operacionalizarlos como tales.

Artefacto SDD Rol en el Harness
spec.md / PRD.md Guide Computational — feedforward con intención estructurada
AGENTS.md Guide Computational — reglas y restricciones para el agente
Criterios de Aceptación (CA) Definen los targets de Sensors — "pasó = adherente a la spec"
Tests (CI/CD) Sensor Computational — feedback determinístico
Skills.md Guide Inferential — contexto especializado bajo demanda
Si practicas SDD, ya estás haciendo Harness Engineering.
Harness Engineering es el nombre de lo que haces cuando cuidas los artefactos SDD con rigor operacional.

El ciclo

① Spec (SDD) → Guide feedforward para el agente
② Agente genera → Sensor Computational evalúa
③ Falló → itera hasta que los Sensors pasen
④ Pasó → humano revisa resultado, no proceso
Codex, de OpenAI (2025): "Our biggest challenges now center on designing environments, feedback loops, and control systems" — 1 millón de líneas de código con cero líneas escritas manualmente.

La tabla es el puente entre lo que el público ya conoce (artefactos SDD) y el nuevo vocabulario (Guides/Sensors). No hay que reaprender nada — es reconocer lo que ya hacen con el nombre correcto.
